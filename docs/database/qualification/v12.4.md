# Stable v12.4 port qualification

This record covers the preparation branch `port/stable-v12.4`. It records tests of the stable port; it is not a
published fork release or evidence of an upgrade of a production installation.

## Provenance and packaging

- Upstream baseline: [Jellyfin v12.4](https://github.com/jellyfin/jellyfin/releases/tag/v12.4), commit
  `83d0d0e7f76e23e2e085c8ff67d28b772d35967d`. This was the latest non-prerelease on 2026-11-09.
- Fork changes were applied from `fork/maintenance-foundation` at `8c52b47bdc`. That branch remains as development
  history. The stable port starts at the stable tag and does not merge upstream development history.
- Source port commit: `1b04b7ce59493f7af05456bff0ecaf94818193f4`.
- Stable upstream package versions and the EF tool remain at 10.0.14. The added SQL Server provider and PKCS
  dependency also use 10.0.14. No existing stable package version was downgraded.
- The API-key tests that depend on an unreleased upstream API response were omitted. Subtitle regression tests use
  the stable API without importing the development branch's new timestamp-map parameters.
- The Compose image uses upstream `jellyfin/jellyfin:12.4` pinned to manifest digest
  `sha256:fea863d0cd9ec445985d9c75fc6ed64e38a1d2766cf0c250a33d553f4fc1b771` for its web client and FFmpeg.
- Packaging commit `e86887e4b99490e41f9957ea7e5a603a34290b01` pins SDK 10.0.403 to manifest digest
  `sha256:212fe4cb74627d5adf9817a4088906ae3edff1bd853bb27565d4b46731efe61e`. SDK 10.0.401 bundled 10.0.12;
  updating the SDK avoids downgrading the self-contained runtime relative to stable upstream.

## Automated tests

The [source-port Tests run](https://github.com/shea786/jellyfin/actions/runs/42607165195) passed all four jobs:

- Ubuntu: 6,222 passed, 202 skipped, no failures.
- macOS: 6,189 passed, 235 skipped, no failures.
- Windows: 6,184 passed, 240 skipped, no failures.
- PostgreSQL 16: 3,225 passed, 183 skipped, no failures across the implementation, server and integration projects.

Skips include tests for other providers and platform-specific cases. The database workflow requires the backend
sentinel in each project and the `DatabaseRestoredFromPgDump_CanBeGroupedByPresentationKey` test to pass; a
SQLite fallback cannot satisfy those checks. The full suites include migration contents, model/snapshot parity,
provider conformance, startup, backup and restore coverage.

The [source-port Format run](https://github.com/shea786/jellyfin/actions/runs/42607165073) passed.
Local Release compilation completed with zero warnings and errors. Debug compilation, including the database SQL
ban analyzers, completed with 215 advisory warnings and no errors. Local formatting and generated operator-document
checks passed.

One local networking test failed because the host resolved `invalid.domain.test` instead of returning DNS failure.
Its eight-case theory passed in a container with external networking disabled, and the complete networking suite
passed on all three hosted runners. No production networking code was changed for this host-specific result.

The hosted runs use SDK 10.0.403 and runtime 10.0.14. The packaging-head reruns both passed:
[Tests](https://github.com/shea786/jellyfin/actions/runs/42616299078) and
[Format](https://github.com/shea786/jellyfin/actions/runs/42616299376), on commit
`e86887e4b99490e41f9957ea7e5a603a34290b01`.

## Disposable installation, upgrade and recovery

The final image built from packaging commit `e86887e4b9` passed all 44 assertions in the
[installation results](v12.4-installation-results.json). The local image ID was
`sha256:de39a06e10c8b7dc339ad4b2814511148547138733459b5f730800aef1a4cb3c` on Linux amd64.
Its runtime configuration reports both `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` at **10.0.14**.
FFmpeg reports **8.1.3-Jellyfin**. The image was built locally and was not published to a registry.

The API client used Python's HTTP library with MediaBrowser authorization and a disposable administrator account.
No GUI client or production library was involved. The fixture was a fresh official 12.4 SQLite installation with
two generated 12-second H.264/AAC movies, local NFO metadata and JPEG artwork. One movie was marked watched;
the other was stopped at three seconds after lowering the minimum resume duration for this fixture.

The sequence was:

1. Start the pinned official 12.4 image with a disposable configuration directory. Complete its startup wizard,
   create the local movie library, scan both movies and set the watched/resume states through the API.
2. Stop the official server cleanly. Start the fork's final image on the same SQLite configuration and data.
   Confirm the movie ID, watched state, three-second resume position, artwork and playback information. Request a
   1,024-byte range from the static video stream and verify the response length.
3. Create a Jellyfin backup through `POST /Backup/Create` and stop the SQLite server cleanly. Capture row counts
   from the stopped SQLite database: **9 BaseItems, 1 User, 2 UserData rows and 1 Peoples row**.
4. Start a disposable PostgreSQL 16.15 server. Copy the fixture configuration and files, select the PostgreSQL
   provider, reset the fixture's wizard-completed flag for its empty target database, and start the fork once to
   create the PostgreSQL schema. Stop it, restore the completed-wizard flag, then restart with `--restore-archive`
   pointing to the SQLite backup. Preserve the target provider configuration throughout the restore.
5. Repeat the identity, watched/resume state, artwork and direct-stream checks. Query the actual PostgreSQL tables
   and require each of the four captured row counts to match SQLite exactly. Create another user through the API
   to verify writes after restoration.
6. Create a PostgreSQL backup, delete that new user, stop the server and restore the backup through
   `--restore-archive`. Confirm the user's recovery and repeat the movie, watched/resume, artwork and playback checks.
7. Remove all disposable Jellyfin and PostgreSQL containers.

A separate empty-directory start of the final fork image passed five further
[fresh SQLite checks](v12.4-fresh-sqlite-results.json): startup wizard, health endpoint, serving the stable web client,
creating an administrator, and retaining that account after a container restart. This brings the real-image
qualification to **49 passing assertions**.

To repeat the source checks locally, use the SDK selected by `global.json`:

```sh
dotnet build Jellyfin.sln --configuration Release
dotnet test Jellyfin.sln --configuration Release --no-build
# Repeat for each of Jellyfin.Server.Implementations.Tests, Jellyfin.Server.Tests and
# Jellyfin.Server.Integration.Tests; Testcontainers starts an isolated PostgreSQL server.
dotnet test tests/Jellyfin.Server.Implementations.Tests --configuration Release --settings tests/postgres.runsettings
dotnet format --verify-no-changes
docs/database/render --check
docker build -f docs/database/compose/Dockerfile -t jellyfin-multidb:12.4-port .
```

The HTTP qualification sequence above is recorded separately from the automated suites: it verifies real image
startup and data movement across engines, while the suites exercise many additional failure cases.

## Remaining release work

The supported targets remain SQLite and PostgreSQL; MySQL/MariaDB and SQL Server remain experimental. This port's
runtime qualification does not promote the experimental providers. Their actual-engine matrix still needs a fresh
run before a preview release advertises their current results.

Repository activation (the maintained default branch, branch protections, fork support channels), release versioning
and publication remain separate work. OpenAPI, ABI and CodeQL were not part of these push-triggered runs. Full
release qualification must also consider representative large libraries, plugins, remote clients, transcoding and
additional architectures; the disposable fixture below covers a small local library and direct playback.
