## Why it exists

Two things kept shared code honest only by luck.

- **Raw SQL and engine checks.** Production code that runs raw SQL, or asks which engine it runs on, works on that engine only. Nothing told a contributor so.
- **Engine hazards.** The suite checks what the server does. It passes on an engine as long as the queries it happens to run work there, so some hazards never came up in it:
  - the depth of a cascade;
  - the host time zone;
  - LIKE metacharacters;
  - long id lists;
  - long composite keys.

22d adds a compile-time ban for the first and a cross-engine conformance kit for the second (ADR-0001 W5). It also gives Server.Tests a sentinel of its own (B21).

## The ban (`98dcacbfc6`)

**What it bans.** `BannedSymbols.Database.txt` has 25 ids, each with a message that names the alternative.

| Group | Members |
|---|---|
| Raw SQL | `ExecuteSqlRaw`, `ExecuteSql` and `ExecuteSqlInterpolated`, with their async forms; `SqlQueryRaw` and `SqlQuery`; `FromSqlRaw`, `FromSql` and `FromSqlInterpolated` |
| The connection | `GetDbConnection`, whose commands are raw SQL too |
| Engine checks | `IsSqlite`, `IsNpgsql`, `IsMySql` and `IsSqlServer`, on both `DatabaseFacade` and `MigrationBuilder`; `DatabaseFacade.ProviderName`; `MigrationBuilder.ActiveProvider` |

**Every overload is listed.** The analyzer bans nothing for an entry without a parameter list.

**Checking the ids.** The analyzer also silently ignores an entry that names no symbol, so the ids need their own check.
- **The test.** `DatabaseBannedSymbolsTests` resolves every entry by reflection against the EF Core and provider assemblies the test project loads.
- **Pinned entries.** Only entries for a provider assembly that does not load at all use a pinned list in the test: SQL Server, and MySQL where it is not referenced. The pinned exemption applies only on `FileNotFoundException`.
- **Package docs.** All 25 ids were checked against the documentation XML of the packages at 10.0.12, and Npgsql at 10.0.3 (`/tmp/22d/ban-ids/`: `verification-after-fix.txt` has 25 FOUND, 0 NOT FOUND). The SQL Server package was downloaded to read its XML only; nothing in it was executed.

**Where it applies.** `Directory.Build.props` adds the file to every project except two kinds:
- projects whose name starts with `Jellyfin.Database.Providers.`, where such code belongs;
- projects under `tests/`, because a test may be about one engine.

The rule depends on the project's path only, normalised and compared without regard to case. There is no opt-out property, because MSBuild imports environment variables as properties, so a property could be switched off from outside. Like the other banned APIs, the ban is checked in Debug builds.

**Existing call sites.**
- **7 production sites are suppressed in place**, each scoped, with its reason:
  - two in `BackupService` and three in `JellyfinMigrationService`, which run the migration history scripts generated by the provider in use;
  - `MigrateActivityLogDb` and `StripEmbeddedLinkedChildren`, legacy routines that only ever run on SQLite.
- **4 file-wide `RS0030` disables used no banned API, so they were removed.** They were in `MigrateLibraryDb`, `MigrateLibraryDbCompatibilityCheck`, `FolderAwareFilterExtensions` and `JellyfinQueryHelperExtensions`. The ban now reaches those files.
- **20 file-wide `RS0030` disables remain and still hide the ban** (follow-up 1, below). They are upstream files that disable `RS0030` for the Guid operators inside query expressions. The analyzer, 5.6.0, reports every banned-symbols file under the one id `RS0030`, so the ban cannot get an id of its own that those disables would leave on. The commit message lists the 20 files.

**Scope decision.** The implementer reported that the first version of the ban needed 109 suppressions: 7 in production and 102 in tests. My union of the call-site lists in `/tmp/22d/dev/ban-sites*.txt` gives 109 sites, 107 of them under `tests/`. The difference is unreconciled, and neither figure is preferred here. The coordinator narrowed the ban to production code, because tests may be engine-specific by design; `ProviderFact` and the known gaps already keep those honest.

## The time zone helper (`cddbb29d77`)

`TemporaryTimeZone` moves into `Jellyfin.Database.Testing`, because a kit row runs under a time zone that is not UTC, and the kit lives there. Its behaviour does not change. The collection that keeps such tests from running in parallel stays in the test project, because xUnit only reads collection definitions from the test assembly.

## The kit (`6ba81682b7`, `d6b1d8169b`)

**Structure.**
- **Rows.** Each row is an abstract class in `Jellyfin.Database.Testing.Conformance`, run by a sealed class in `Jellyfin.Server.Implementations.Tests`. Rows work through the model, LINQ, the provider's members and the server's services, never with SQL of their own.
- **Tables.** `ModelRowFactory` builds a valid row for any table, so a table added later is covered without a change to the kit.
- **Engines.** `ConformanceKit.Engines` is SQLite and PostgreSQL. On any other engine every row skips.

**55 cases:**

| Row | Cases | What it checks |
|---|---:|---|
| Purge | 6 | Exactly the given tables are emptied, identities restart at 1, and a database from the backend holds only seed data. |
| Restore | 2 | Explicit identities are kept and the next one is higher, and a backup of every table restores exactly. |
| WriteConflict | 4 | A lost race on a key or unique index is retryable to the classifier, and a missing required value or foreign key is not. |
| FolderDelete | 2 | A folder above a `ParentId` chain of depth 20, and one in its middle. |
| DateTimeLimits | 12 | `MinValue` and `MaxValue` of every kind, in every date column, under New York and Kolkata time. |
| Like | 18 | `%`, `_`, the escape character, ASCII case and other characters, for contains and starts-with. |
| IdList | 8 | 3,000 and 100,000 ids through `WhereOneOrMany` and through a plain `Contains`. |
| CompositeKey | 1 | Every key of bounded strings at full length, in three-byte characters. |
| Model | 2 | The provider's model has the SQLite model's shape, and every table round-trips a full row. |

The brief I was given said Purge 5. The TRX files show 6, which is what makes the total 55.

**Results on the fork, from the TRX:**
- **SQLite:** 53 passed, 2 skipped by the known gap `SQLITE-CONTAINS-PARAMETER-LIMIT`. A plain `Contains` over 100,000 ids exceeds SQLite's 32,766 parameters. `WhereOneOrMany`, which shared code uses for long lists, passes.
- **PostgreSQL:** 55 passed.
- **MySQL and MariaDB:** all skipped until 27a adds them to `ConformanceKit.Engines`. Each run reports 23 skipped kit results.

**Exceptions in the restore row.** Two exceptions are written so that they expire on their own:
- `HomeSection` is listed as not carried by a backup;
- concurrency tokens (RowVersion) are left out of the comparison.

Each fails the row once a restore gives the data back, which tells the next person to remove the exception. No fork ids appear in the shipped kit or ban text (H10; a grep of the kit, the test classes, the ban file and its test found none).

**The purge tests.** `d6b1d8169b` removes `SqliteDatabaseProviderPurgeTests` and the PostgreSQL purge tests for a plain table name and for no tables, which the purge row now covers on every engine. The PostgreSQL tests for schema-qualified and quoted names stay.

## The Server.Tests sentinel (`580005950e`)

`ProviderBackend_IsLive` now runs in `Jellyfin.Server.Tests` too, through the same `BackendLiveness.Verify`. It fails in three cases:
- `JELLYFIN_TEST_EXPECTED_PROVIDER` names another provider;
- the server cannot be reached;
- the server is older than the supported version.

It prints the backend and server version. A Server.Tests run now proves its own backend, which closes B21.

## Findings

- **F1 = X10: `HomeSection` is lost on restore, on every engine.** A backup does not carry it (it has no set on the context), and the purge of `DisplayPreferences` deletes its rows in cascade. A fix task is starting separately. The restore row's exception expires when it lands.
- **F2: concurrency tokens are restored as 0.** No concrete harm is known. It is an upstream-note candidate.
- **F3: a plain `Contains` with 100,000 ids fails on SQLite.** Upstream-note candidates, with lines at `580005950e`:
  - `LinkedChildrenService.cs:93`;
  - `BaseItemRepository.TranslateQuery.cs:319`;
  - `ItemPersistenceService.cs:403`, `457`, `531` and `601`. On the fork these lines are 11 later.
- **F4: a partial purge differs between engines.** PostgreSQL uses `TRUNCATE ... RESTART IDENTITY CASCADE`, which also empties dependent tables. SQLite turns foreign keys off (or defers them in a transaction) and can leave orphans. Every current caller purges all tables; the only production caller is `BackupService`'s restore. A contract note or a 27a kit row.

## Follow-ups

The implementer's follow-ups, numbered as in the implementer's report. Items 2 to 10 are the implementer's words, verbatim, as relayed:

1. The 20 file-wide `RS0030` disables still hide the ban, because analyzer 5.6.0 reports every banned-symbols file under the one id `RS0030`. A dedicated analyzer rule is planned for 27a.
2. Banned-symbol test TypeId: a generic declaring type is rendered wrongly and indexers aren't handled. Both can only cause a false failure.
3. The ban is Debug-only, which is the existing pattern.
4. ModelConformance compares the model with itself on SQLite, so it's meaningful only on PG.
5. The two SQLite-only routines (MigrateActivityLogDb, StripEmbeddedLinkedChildren) have no guard against another engine.
6. The CI sentinel check should be per project (step 26).
7. 27a: the sentinel doesn't tell MySQL from MariaDB. Fix it by comparing the server-reported flavour (MariaDB marker) with the selected provider, plus a negative control, using EngineTraits.
8. The commit body could name MySqlRestoreIdentityTests and MySqlPurgeDatabaseArgumentTests (optional, not done).
9. 27a: check whether the kit duplicates those MySQL classes.
10. H10: no fork ids in shipped text.

Also planned for 27a, from the merge: the MySQL and MariaDB kit rows, after which the MySQL purge test class can go.
